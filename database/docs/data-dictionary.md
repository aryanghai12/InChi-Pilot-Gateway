# Buyer Requirement Data Dictionary

This document defines the proposed database concepts for the buyer-demand
schema. It is a draft companion to the field mapping and does not override the
Excel field dictionary or BNCS approvals.

## Entity definitions

| Entity | Definition | Lifecycle |
|---|---|---|
| `BuyerRequirement` | Stable identity and current workflow state for one buyer demand record | Created, edited through new versions, submitted/reviewed, archived |
| `BuyerRequirementVersion` | Immutable material snapshot used for traceability and matching | Created on initial save and material changes; never updated |
| `RequirementSpecification` | Category-specific structured product attributes | Tied to a requirement version and schema version |
| `RequirementQuantity` | Requested amount, unit and frequency | Tied to a requirement version |
| `RequirementCommercialTerms` | Price range, currency and price basis | Tied to a requirement version; access-controlled |
| `RequirementDelivery` | Destination, delivery window and lead time | Tied to a requirement version |
| `RequirementEvidenceCriterion` | Required document/certification criterion | Tied to a requirement version and approved taxonomy |
| `RequirementEligibilityCriterion` | Mandatory candidate condition | Evaluated before preferences |
| `RequirementPreference` | Non-mandatory desired attribute | Used only after mandatory eligibility |
| `MatchingReadinessBlocker` | Specific unresolved reason preventing matching | Derived from approved gate configuration |
| `MatchingConfiguration` | Versioned approved criteria/weights/configuration reference | Inactive until approved |

## State and provenance rules

- IDs are generated by the database/application and are immutable.
- Timestamps use one agreed UTC convention.
- Every material version records the actor and change time.
- A match run must reference a specific requirement version.
- A requirement's current status is separate from completeness.
- Completeness is separate from matching readiness.
- Missing, unknown and not-applicable values must remain distinguishable where
  the field participates in eligibility.
- Audit data must not contain passwords, tokens, secrets or unnecessary
  personal data.

## Type guidance

- Use UUIDs for primary keys and foreign-key identifiers.
- Use `Decimal` for quantity and monetary values.
- Use reference/configuration records for markets, categories, units,
  currencies, evidence types and workflow states.
- Use JSONB only for category-specific specifications and structured criteria
  whose schema is versioned.
- Use date fields for delivery dates and document dates; apply the approved
  timezone convention to timestamps.

## Minimum index guidance

Index the fields used for ownership, workflow and matching queries:

- requirement status
- completeness status
- matching readiness
- owner
- target market
- product category
- created and updated timestamps
- requirement/version pair
- active configuration and approval state

## Required review before model implementation

The team must confirm the open decisions before finalising:

1. Buyer organisation representation
2. Product taxonomy representation
3. Approved units and currencies
4. Requirement workflow states
5. Completeness and matching-readiness gate
6. Eligibility and preference vocabulary
7. Version and audit retention policy
8. Field-level permission rules
