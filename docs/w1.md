## 1. Test Strategy

### 1.1 Objective

Establish a consistent approach to verifying the functional correctness, access control, data integrity, validation and auditability of the InChi Pilot Gateway.

The initial strategy covers the first four user-journey stages:

1. Access workspace
2. Register supplier and product
3. Assess China readiness
4. Capture buyer requirement

The strategy prepares the project for repeatable testing as the frontend, backend and database components become available.

### 1.2 Testing approach

| Test level | Purpose | Initial focus |
|---|---|---|
| Smoke testing | Verify that essential functionality is usable after a build or deployment | Authentication, protected routes, core record operations and validation |
| Functional testing | Verify that features behave according to acceptance criteria | Login, supplier/product CRUD, readiness and buyer requirements |
| Negative testing | Verify that invalid or unauthorised operations fail safely | Missing fields, invalid inputs and denied access |
| API testing | Validate server-side behaviour and response contracts | Authentication, validation, permissions and persistence |
| Integration testing | Verify that connected components work together | API, database, workflow and audit events |
| Regression testing | Ensure fixes do not break existing functionality | Previously passed smoke and functional cases |
| Audit and security testing | Verify access enforcement and traceability | Role restrictions, denied actions and change history |

### 1.3 Risk-based priorities

**P0 — Critical controls**
- Unauthorised users cannot access protected data or perform restricted actions.
- Invalid or incomplete data cannot bypass mandatory validation.
- Material changes and required denied-action events are traceable.

**P1 — Core functionality**
- Users can create, retrieve, update and search supplier/product records.
- Readiness assessments enforce mandatory information and review rules.
- Buyer requirements are validated and saved correctly.

**P2 — Additional coverage**
- Boundary-value validation, unusual input combinations, error handling and regression scenarios.

These priorities are provisional. Final severity and release-blocking rules should be agreed with the project lead.

### 1.4 Entry criteria

Testing may begin when:
- The relevant application component is available in a test environment.
- Acceptance criteria and expected behaviour have been agreed.
- Test accounts and role permissions are available.
- Required API contracts and test data are available.
- The test environment can be accessed reliably.

### 1.5 Exit criteria

A test cycle can be considered complete when:
- Planned smoke tests have been executed and results recorded.
- All critical test failures have been investigated.
- Defects are logged with evidence and assigned an owner.
- Critical and high-severity unresolved issues are reported to the project lead.
- Test results and outstanding risks are documented.

Passing smoke tests alone does not establish that the entire application is ready for release.

### 1.6 Test tools

- **Playwright:** browser-based end-to-end testing and API checks.
- **pytest:** backend testing, if adopted by the implementation team.
- **Vitest and React Testing Library:** frontend component testing.
- **GitHub Issues:** defect tracking, if confirmed as the team's agreed workflow.
- **GitHub Actions:** automated test execution when CI is available.

Tools and commands will be confirmed against the actual repository configuration before execution.

## 3. Smoke Test Cases

These are the initial smoke scenarios for the first four stages of the user journey. They are planned tests, not claims that the application has already passed them.

### Stage 1 — Access workspace

**TC-M1-01: Approved user login**
- Preconditions: Test environment available; valid approved account.
- Steps: Sign in using valid credentials.
- Expected: Authentication succeeds and the permitted workspace is displayed.
- Priority: P0.

**TC-M1-02: Unauthenticated protected access**
- Preconditions: No authenticated session.
- Steps: Navigate directly to a protected page and request a protected API.
- Expected: Access is denied and protected data is not exposed.
- Priority: P0.

**TC-M1-03: Role-restricted action**
- Preconditions: A test account with limited permissions.
- Steps: Attempt a restricted action through the UI and directly through the API.
- Expected: Both attempts are denied where the action is not permitted; backend enforcement cannot be bypassed.
- Priority: P0.

**TC-M1-04: Denied-action audit**
- Preconditions: Audit logging implemented and the relevant event specified.
- Steps: Attempt a protected action without the required permission.
- Expected: The action fails safely and the required audit event is recorded.
- Priority: P0.

### Stage 2 — Supplier and product registry

**TC-M2-01: Create and retrieve supplier**
- Preconditions: Authorised user and valid test data.
- Steps: Create a supplier, retrieve it by its identifier and search for it.
- Expected: The saved record can be retrieved and returned in search results.
- Priority: P1.

**TC-M2-02: Update supplier**
- Preconditions: Existing supplier record.
- Steps: Update an editable field and retrieve the record again.
- Expected: The updated value persists and the change is traceable where required.
- Priority: P1.

**TC-M2-03: Invalid supplier input**
- Preconditions: Supplier form or API available.
- Steps: Submit a record with a mandatory field missing or invalid.
- Expected: The request is rejected with a useful validation response; invalid data is not silently accepted.
- Priority: P0.

**TC-M3-01: Create product linked to supplier**
- Preconditions: Existing supplier and valid product data.
- Steps: Create a product associated with that supplier and retrieve it.
- Expected: The product persists and references the correct supplier.
- Priority: P1.

**TC-M3-02: Invalid supplier reference**
- Preconditions: Product creation endpoint available.
- Steps: Submit a product with a nonexistent or inaccessible supplier reference.
- Expected: The relationship is rejected according to the agreed API contract.
- Priority: P1.

### Stage 3 — China readiness

**TC-M4-01: Incomplete assessment**
- Preconditions: A valid supplier/product record and an assessment form.
- Steps: Leave a mandatory question unanswered and attempt submission.
- Expected: Submission or progression is blocked and the missing information is identified.
- Priority: P0.

**TC-M4-02: Assessment review permissions**
- Preconditions: Accounts representing a permitted reviewer and a non-reviewer.
- Steps: Attempt to record a review outcome with each account.
- Expected: The permitted reviewer can perform the authorised action; the non-reviewer is denied.
- Priority: P0.

### Stage 4 — Buyer requirement

**TC-M5-01: Create valid requirement**
- Preconditions: Authorised user and agreed mandatory-field rules.
- Steps: Complete the buyer requirement form and save it.
- Expected: The requirement is persisted and can be retrieved.
- Priority: P1.

**TC-M5-02: Block incomplete requirement**
- Preconditions: Buyer requirement form or API available.
- Steps: Omit a mandatory input and attempt to mark the requirement ready.
- Expected: The transition is rejected with a clear explanation; matching cannot begin with an incomplete requirement.
- Priority: P0.

**TC-M5-03: Requirement versioning**
- Preconditions: Versioning implemented and a saved requirement available.
- Steps: Modify a requirement and inspect its history.
- Expected: The change follows the agreed versioning rules, and historical versions remain traceable.
- Priority: P1.

### Smoke test execution record

For every test, record:
- Build or commit identifier.
- Test environment and timestamp.
- Tester and test account role.
- Actual result and status.
- Screenshot, API response or log reference.
- Linked defect ID, if applicable.

Do not mark a scenario as passed until it has been executed against a working implementation.

## 4. Defect Management Workflow

### 4.1 Defect lifecycle

`New → Triaged → Assigned → In Progress → Fixed → Retest → Closed`

Alternative outcomes:
- **Reopened:** The defect persists after the proposed fix.
- **Blocked:** Testing cannot proceed because a dependency is unavailable.
- **Rejected / Duplicate / Deferred:** Used only after review and with a documented reason.

### 4.2 Defect reporting requirements

Every defect should contain:
1. Unique defect ID and descriptive title.
2. Related requirement and test-case ID.
3. Environment and build/commit identifier.
4. Preconditions and reproducible steps.
5. Expected result and actual result.
6. Severity and priority.
7. Supporting evidence, with sensitive information redacted.
8. Assigned owner and current status.
9. Retest outcome and closure evidence.

### 4.3 Severity definitions

| Severity | Definition | Example |
|---|---|---|
| Critical | Serious security exposure, unauthorised access to sensitive data, or major data-integrity failure | Restricted user can retrieve protected supplier records |
| High | Major required workflow fails or a significant control is bypassed | Incomplete readiness assessment can progress despite mandatory checks |
| Medium | Important functionality is incorrect but a reasonable workaround exists | Supplier search returns incomplete results |
| Low | Minor usability, cosmetic or non-blocking issue | Misaligned validation message |

Severity describes impact. Priority determines how urgently the team should address the issue. The project lead and QA should agree on final classifications during triage.

### 4.4 Triage and ownership

- **Harish (QA):** Reproduce the defect, assess impact, attach evidence, link requirements, retest fixes and maintain the defect register.
- **Relevant developer:** Investigate the root cause, implement the fix and identify regression risks.
- **Project lead / designated reviewer:** Resolve priority conflicts, decide deferrals and confirm release-blocking issues.
- **Security or data owner:** Participate when access control, sensitive information or audit integrity is affected.

### 4.5 Retesting and regression

After a fix is delivered:
1. Confirm the fix is available in the correct environment.
2. Rerun the original failed test.
3. Verify the affected API, UI and persisted data as applicable.
4. Run related regression tests.
5. Attach new evidence.
6. Close the defect only when the expected result is confirmed.

If the issue remains, reopen it with updated reproduction steps and evidence.
